Trace the architecture

Follow knowledge from source to verified evidence.

Switch paths, select a stage, and see which component owns the decision. One store is authority, one preserves evidence, and two are rebuildable projections.

Select any stage to inspect its contract.

Visibility invariantcandidate.version == authority.active_version
Connector boundary

Describe before expensive work.

Discovery returns a lightweight, stable locator. Descriptor admission checks tenant scope, identity, policy, and change signals before content is fetched.

  • Source-specific pagination and auth
  • Early incremental checkpoint
  • No scheduling policy in connectors
Orchestration boundary

Durable coordination, shared policy.

Temporal records ingestion progress and retries external activities. Direct and distributed executors still call the same engine rules.

  • Replay-safe workflow decisions
  • Idempotent activity effects
  • Pause, resume, and graceful cancel
Evidence boundary

Immutable inputs make replay possible.

Raw, parsed, canonical, chunk, representation, and manifest artifacts are versioned outside the search indexes.

  • Inspectable provenance
  • Connector-free reindex
  • Search stores are not the source of truth
Policy boundary

Preserve structure for retrieval.

Source-aware planning produces addressable route and evidence chunks. Provider-neutral model ports encode dense, sparse, or both representations.

  • Tables remain first-class
  • Vector space identity is explicit
  • Provider SDKs stay in adapters
Projection boundary

Indexes are replaceable views.

Qdrant receives versioned vector records. FalkorDB receives deterministic structure and relationships already declared by a source.

  • Tenant and version addressed
  • Manifests support verification
  • Both rebuild from artifacts
Authority boundary

Publish only after verification.

PostgreSQL advances the active-version pointer atomically after required projections verify. Delayed cleanup never makes a partial version authoritative.

  • One visibility decision
  • Failed versions remain inactive
  • Cleanup is independent repair work
Access boundary

Every query begins with scope.

SDK, CLI, HTTP, and MCP normalize requests into a provider-neutral query with required tenant and principal context.

  • MCP exposes governed retrieval only
  • Transport schemas stay bounded
  • Raw credentials never enter results
Retrieval policy

Select lanes without workflow latency.

The direct read path plans dense, sparse, or hybrid retrieval, applies budgets, and normalizes provider candidates.

  • Temporal is not on the query path
  • Ranking policy stays in engine
  • Provider responses are not contracts
Search projection

Fast candidates are provisional.

Qdrant returns tenant- and version-addressed candidates. Similarity alone cannot make content visible.

  • Dense and sparse lanes
  • Version identity on every record
  • Stale data can be rejected safely
Visibility check

Authority filters every candidate.

The candidate document version must equal PostgreSQL's active version and satisfy the request access context.

  • Safe during republish
  • Safe during delayed cleanup
  • Safe after partial provider failure
Grounding boundary

Return addressable evidence.

Accepted candidates resolve to immutable content and evidence ranges with normalized provenance, not just detached index text.

  • Auditable source location
  • Stable byte or element ranges
  • Artifacts outlive projections
Optional expansion

Add bounded structural context.

Graph traversal can add containment and source-declared relationships. It does not claim automatic entity resolution or extracted facts.

  • Deterministic graph scope
  • Dedicated graph tools available
  • Vector evidence can stand alone
Architecture with boundaries

Adopt a platform.
Keep your options.

Eight focused Python packages keep domain contracts independent from provider SDKs, workflows, interfaces, and deployment composition.

  • Provider SDKs stay in adapters
  • Domain behavior tests without live services
  • Dependency direction enforced in CI
  • Replace providers capability by capability

Built for operators and builders

Useful from the first command. Controllable at every stage.

Start with local development, inspect the live pipeline, and expose retrieval through the interface your application needs.

# Submit an ingestion workflow and wait for completion
harborrag ingest start \
  --tenant engineering \
  --connector github-main \
  --wait

# Retrieve with hybrid search and graph context
harborrag retrieve "How do we release safely?" \
  --tenant engineering \
  --lane hybrid \
  --graph \
  --json
# Submit an incremental ingestion through the control-plane API
curl --fail-with-body \
  --request POST \
  --header 'Content-Type: application/json' \
  --data '{"connection_id":"github-main", \
           "tenant":"engineering", \
           "mode":"incremental"}' \
  http://127.0.0.1:8000/v1/ingestions
# Governed retrieval through the MCP tool boundary
result = await server.call_tool(
    "vector_search",
    {
        "query": "How do we release safely?",
        "tenant_id": "engineering",
        "top_k": 5,
    },
)
# Use the stable async SDK facade
access = AccessContext(
    principal_id="user-1",
    tenant_id="engineering",
)
async with HarborRAG.from_config("harborrag.yaml") as harbor:
    results = await harbor.retrieval.search(
        RetrievalRequest(access=access, query="release safety")
    )
